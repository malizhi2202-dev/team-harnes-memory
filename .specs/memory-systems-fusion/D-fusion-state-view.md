## ① 头脑风暴

我们的融合语义在原则层已经很硬（冲突八分类、追加 Revision 不覆盖、生命周期候选态、ChangeSet 唯一审核对象），但**从原则到「用户在屏上可判定」缺三段**：

1. **条目状态表达不完整**（GD-1 高级产品经理修正后判决）：p7 记忆表**已有**「生命周期」列（`_build/protoB.html:395`），`superseded` 在 p8/p9 版本行已有写法（`protoB.html:501/588/609`、`protoC.html:50`）。缺口精确为：条目级演示值全为 active/review_due，**无「被谁取代/是否合成件」的回链、无按状态筛选**。复用既有写法是**降本依据**，不是从零建能力。
2. **读视图不显**。融合之后「默认看到什么」是产品决策：mem0 用三个读挡位（默认含 superseded／`latest_only`／`include_merged`）把选择权做成查询参数+UI 开关。我们没有任何「视图挡位」概念，投影加载（议题 04）只写了按权限裁剪，没写按状态裁剪。
3. **时间轴不显**。血缘记录已经成对携带 **`valid_time`＋`recorded_at`**（议题 07:87-92），资产版本行有 `valid_from/valid_until`（`_build/sec3.html:350`）——双时态在我们模型里**不是外部新概念，只是没上移到条目/Revision 层**；Zep 的 created/valid/invalid/expired 四字段只是同一思想的另一种词形。
4. **写入时机不成维度**。LangMem 把 hot-path（对话内主动写）vs background（会话后反思沉淀）列为一等设计轴；我们议题里有「会话后沉淀」，但从未把「这条记忆是什么时候、由哪条通道写进来的」做成可筛选/可展示的属性。
5. **分层口径对表**（附带）：TencentDB 的 L1 实际 7 类两族而上游 API 文档仍写 3 类——外部「文档落后实现」活标本；我们 `VALIDATION.md` §8 已有 L0/L3 分层口径冲突未裁决。本议题**不裁决口径**，只建议融合态表达设计必须以「§8 裁决结果」为输入，防止在冲突口径上盖楼。

备选形态：a) 只在 p7 既有生命周期列上补回链与筛选（最小，降本路径）；b) 管理轴+召回轴双默认挡位＋双时态上移条目层（完整）；c) 引入外部五态枚举直接替换我们的候选态（否决：把 §10.1 自标「非最终 Schema」的候选口径当冻结面破坏，且无必要）。

## ② 竞品分析

| 系统 | 事实 | 来源（2026-09-22/29 抓取） |
|---|---|---|
| mem0 | 条目自带 `lifecycle_state`/`replaced_by`/`synthesized`/`structured_attributes`/`expiration_date`，五态直接可读；Dream 三动作 Supersede/Merge/Synthesis **全部非破坏**（merged 记录保留、默认隐藏，`include_merged=true` 可取）；读三挡位：默认 active+superseded／`latest_only`／`include_merged`；官方原话「Dream 无任何破坏性操作，每次变更可复核」 | docs.mem0.ai/api-reference/memory/get-memory.md；platform/features/dream.md |
| Zep | 事实失效不删除：新 episode 与旧边比对后由模型裁决，把 `invalid_at` 写在旧边上；双时态四字段 created/valid/invalid/expired（「何时知道它失效」与「事实何时失效」分离）；矛盾不留并列 | help.getzep.com/facts.md；how-graph-creation-works.md |
| TencentDB | 批量 LLM 冲突检测动作 `store|update|merge|skip`，多目标 `target_ids`、跨类 `merged_type`、`merged_priority`、`merged_timestamps`（新旧时间戳并集）；但冲突语义是「静默以新覆盖旧」，**无待裁决队列/无 diff/无置信**——**本项目对该上游的改进清单 B6 亦登记同一缺口**（B6 是我们的改进建议，非对方自认，GD-1 领域专家勘误） | `MemoryCore/src/core/prompts/l1-dedup.ts:35-70,97-134`（上游 ref `v2.0.2-beta.1`）；`.specs/memory-platform-backlog.md` B6 |
| Memobase | 反面：融合=画像覆盖为当前态，无失效时间轴，前后不可追溯（同事实变更无法归因） | docs.memobase.io（全文 grep 无 invalid/TTL 时间轴） |
| LangMem | collection 型入库调和 insert/update/delete-or-invalidate，官方承认「过抽→精度掉，欠抽→召回掉」需 eval 调优；hot-path vs background 写入二分带延迟/召回/算力权衡表 | github langmem conceptual_guide.md |

结论性观察：**三家（mem0/Zep/TencentDB）都收敛到「写侧累积+状态降级，读侧视图开关」的三态分离**；差别在 mem0/Zep 把状态挂在条目上（可判定），TencentDB 只在决策瞬间用（不可追溯）。我们的追加式 Revision 与 mem0 语义同构，**缺的只是把它表达出来**。

## ③ 结论与建议

判断：不新增融合算法、不引入外部枚举；把**已有模型能力翻译成可判定表达**，三项最小增量（GD-1 三票条件已全部内化）：

1. **条目状态回链**：记忆详情在既有「生命周期」列上补「取代链回链（supersedes/superseded 边）」与「合成件标注（derived_from 多父）」两组元素——全部复用 §10.1 既有候选态与议题 07 既有关系词，**不新造状态**。§10.1 是 9 个领域行各自的**候选口径（该节自标「非最终 Schema」）**；本议题只加展示、不触任何 Schema 冻结。
2. **读视图挡位（分轴定默认，GD-1 高级产品经理条件①）**：管理列表与召回投影**两轴分别定默认**——
   - 管理/审核列表默认＝当前有效＋可筛（含 superseded/merged，保历史可见性）；
   - **召回/上下文注入默认＝仅当前有效**；`include superseded` 必须显式勾选并留痕（既有不变量只排除 dispute/隔离/撤回——`sec4.html:168`、`sec5.html:412`——对 superseded **从未定档**，这正是要裁决的产品缺口，不能用「与 mem0 一致」把它默认成「被取代的事实默认进模型上下文」）。
   - 两轴共用同一组挡位语义，**不许两把答案**。
3. **双时态上移（GD-1 领域专家条件③）**：条目/Revision 层的时间语义**一律复用既有词对 `valid_time`/`recorded_at`**（议题 07:87-92；资产版本行已有 `valid_from/valid_until`，sec3.html:350），**不引入 Zep 四字段新词**。AC 裁决序写死：状态=系统裁决、valid/invalid=业务事实区间，两轴正交；as-of 查询必须显式声明；同一问题不得有两个「当前生效」答案。挂点修正：真正的约束来自议题 07 词表与 §10.1「不冻结」声明；§8 四组口径冲突不含时间语义（`VALIDATION.md:185-193`），此前挂 §8 属过度前置，改挂后此项可与 §8 裁决并行。
4. 附带登记：写入通道（对话内/会话后）作为记忆的可筛选属性列入候选；分层口径以 §8 裁决为前置。

**建议改动清单（列表级，不改原型）**
- `1-requirement`：US 候选「融合状态可见可筛」3 条（对应上 1/2/4）+ AC 以可判定输出措辞（哪个屏、哪一挡、看到什么；召回轴默认仅当前有效）。
- `2a-ui-design`/原型 `_build/sec5*.html`（p7 记忆与空间策略屏区）：建议增「取代链回链＋合成件标注＋按状态筛选/挡位控件」元素（沿用既有生命周期列与 superseded 写法，**降本**）；血缘详情联动部分移交 D-2，不在此重复。
- `PRODUCT-DESIGN §2.3/§10.1`：术语表补「读视图挡位（管理轴/召回轴分默认）」条目；双时态用词登记为 07 词对的**上移**而非新造。
- platform 议题 04（按需加载）：建议以「补录轮」追加「按状态裁剪视图（召回默认仅当前有效）」一句到已确认原则下——**属修订已确认议题，需人审背书才可动**（此处仅登记）。
- 不做：外部阈值/参数导入、外部枚举替换候选态、融合算法变更。
