1 · 产品全景

本章回答：这个产品是什么、给谁用、能做什么、以及最重要的——它明确不做什么。

1.1 一句话定位

Enterprise Agent Memory Platform 是外部 Harness 的记忆、知识、血缘与治理平台。Harness（Codex、Claude Code、DSH 等）负责执行工作；平台负责保留、理解、授权、复用、撤回、验证并审计工作证据。

1.4 这个产品不做什么（边界）

边界即需求。以下每一条都是明确的产品承诺，越界即视为缺陷。

不做理由 / 替代做法
不做新的 Agent Harness 或编排运行时执行属于 Codex / Claude Code / DSH 等外部 Harness；平台只治理证据与记忆，不接管执行循环。
不提供 public Memory长期 MemorySpace 的 owner 只有 user | team | project | agent 四类。需要跨边界复用时走「分诊 → 脱敏 → 审核 → 发布为 Wiki / Skill / Template」。
不用一张泛化 Asset 表替代专业资源Wiki、Code、Skill、Template、Memory 各有来源、版本、编辑与阅读语义；资源库只做授权后的发现与跳转，不编辑。
不把「关联 / 可见」当作「可写 / 可执行」owner ≠ visibility ≠ ACL ≠ execution authority；发布或检索不授予执行权。
不在原型里执行真实副作用不真实删除、不擦除终端、不迁移、不发送通知、不跑生产 Run、不暴露凭据明文。
不把阶段性方案写成最终结论Schema、阈值、算法、SLA、责任矩阵、合同与法域模板一律标注待确认，实现前另开 change。
不创建第二套并行信息架构本轮收敛到唯一导航（工作 / 知识与复用 / 输入与治理 / 组织与平台），历史 final-v1、redesign-v2、redesign-v3 只作参考、不修改。
不用单一绿色标签掩盖未知unknown ≠ zero；无法证明时显示「未知 + 范围 + 证据时间 + 下一门槛」。

1.5 竞品格局与我们的差异位

本节回答：市面上已经有什么、它们把什么做成了默认动作、本平台站在哪里。事实底座是 2026-09-22 的四份联网调研稿 _research/RECON-*.md（每条结论带来源与【源码已落地 / 文档声称 / 营销宣传】档位，未验证项如实标注）；本增量已于 2026-09-22 18:56 过人工审核门（用户原话「通过」）。

先说结论

全行业把「把记忆记下来」卷成了成熟件（异步 LLM 抽取、原始层无损留底、软删失效、namespace 隔离、前后台双分工）；但没有一家把「候选 → 人工审核 → 受控发布 → 可证明撤回 → 行动前准入」做成对象链路——头部玩家甚至正在放弃写入期的自动裁决。本平台的差异位不是「抽取更准」，而是把记忆当作可审计、可撤回、可执行准入的治理对象。

1.5.1 行业趋同（默认动作，新进入者的门票）

  1. 抽取全异步、LLM 为核：没有一家敢在线同步写全量记忆，「写入后延迟可见」是共同契约——本设计的 Import→Triage 链路与之一致；差异在链路终点接人工门。
  2. 原始层无损留底：episode / event / L0 原文永久或按 TTL 保留，派生物只从原文生长——对应 §2.6 不变量⑤「新副本新 revision」。
  3. 失效趋软删/累加，但覆盖式仍存：失效不删（Zep）、隐藏不删（mem0）、累加（mem0 v3）与就地改写+去重即删（AWS/Google）两代方案并存——本设计一律 invalidated/superseded 不物删，删除必须走 §4.6 证明链。
  4. namespace/scope 是隔离原语但全是字符串约定，无平台级 schema 治理——MemorySpace 的 owner 四类型 + 写策略枚举（§2.2/§2.4）是对该空位的第一次结构化回答。
  5. 双 agent 分工：前台轻写、后台专职整理（Letta 首倡，各家以批处理变体重现）——本设计的自动分级 M0/M1/M2 + 巩固走 ChangeSet，等于给后台整理补上门。
  6. 文件/git 隐喻回归（MemFS、虚拟文件树、/memories）对抗向量黑箱；但全部只做版本史，无人做到现实时间线+权限治理同时成立。
  7. 合规=SOC2+BYOK+删除 API 三件套，且审计普遍只覆盖管理面——§2.4 数据面审计与 §4.6 副本闭包是超出门票的部分。

1.5.2 相对独有（调研范围内未见对应物）与相对缺口

独有卖点（截至 2026-09-22 调研零命中）

  1. 人工发布门 Triage→ChangeSet→Review→Publish：无一家有版本化、可回滚的审核对象（Google 最接近也只是喂入预筛条目）。
  2. RunGate 行动准入：无人把「记忆影响行动」当治理对象；Zep 官方明言行动授权留给客户。
  3. CopyInventory 副本闭包：在线/缓存/索引/Embedding/Manifest/备份/Provider/终端的全链路撤回清单无人做；mem0「删 100 报成功」与 ChatGPT 30 天窗口证明痛点。
  4. Purpose × ACL 双维：竞品 ACL 只答「谁能看」，不答「为何用」。
  5. 跨 Harness 中立 + 工作现场连续性：各竞品绑自家云或自家 harness；Work Thread / ContextManifest 交接无第二家。

相对缺口（诚实清单；竞品已做而本设计未承诺）

  1. 检索内核与延迟工程：hybrid+rerank+预算装配、亚秒级体验是 Zep/mem0 主场；本设计只定义 ContextManifest 契约，内核走实现 change。待确认
  2. 双时间轴现实时间线：Zep 的 valid/invalid 四戳与时点查询；本设计 ChangeSet/Publish 时间 ≠ 现实有效时间。待确认（候选：MemoryItem 增现实有效区间 + superseded_by 关系化，§10.2）
  3. 低摩擦在线写：纯审核流可能牺牲「当场记住」手感（Letta/Memobase buffer 模式赢在此）；缓解方向=个人空间直写 + 团队空间双速审核。待确认（§10.2）
  4. 开发者接入面：三行接入 / MCP / 37 集成页 vs 本设计 Connector 契约先行；生态差距真实。
  5. 开箱画像/模板供给：竞品 topic 模板与 profile 专型降低冷启动；本设计仅 Template/Code Context 抽象。
  6. 成本与时延透明：审核门+重算+闭包的成本结构未讲清，采购对比吃亏点。待确认（§10.1 已标暂缓）
